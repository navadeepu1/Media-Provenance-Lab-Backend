# Media Provenance Lab

## Application and Digital Forensics Guide

Media Provenance Lab is an offline-first investigation platform for examining
digital media and reconstructing suspicious activity from technical evidence.
It combines media provenance analysis with a deterministic digital-forensics
workflow. The system is designed to help an investigator organize evidence,
normalize records into a timeline, identify suspicious patterns, preserve
custody information, and produce an explainable review record.

The platform is deliberately evidence-oriented. It does not claim that a file
is definitively authentic or manipulated, and it does not allow an AI model to
invent findings. Every finding generated by the current investigation engine
is deterministic and cites one or more imported events.

## 1. Who can use the application?

### Digital-forensics investigators

Investigators can create cases, import logs and access records, reconstruct a
timeline, review suspicious findings, attach notes, bookmark important
events, and preserve evidence hashes.

### Incident-response and security teams

Security analysts can use the activity rules to identify authentication
bursts, unusual access, privilege activity, destructive file operations, and
off-hours logons. The timeline filters help analysts narrow activity by
actor, host, source, action, severity, incident, and date range.

### IT administrators and system owners

Administrators can inspect operating-system logs, web-access records, browser
history, application-access records, and filesystem metadata when investigating
an account, host, or service.

### Media-authenticity reviewers

Reviewers can inspect image and video provenance signals, metadata, C2PA status,
compression artifacts, noise residuals, copy-move regions, known-item
similarity, and frame-level video evidence.

### Researchers and educators

Researchers can run the application locally, use fixed-seed synthetic samples,
execute regression tests, and evaluate labeled datasets without sending files
to a hosted AI service.

### Auditors and legal reviewers

Auditors can review event citations, evidence hashes, custody verification
results, audit entries, notes, status changes, and limitations. The local
profile is not by itself a legal certification or a replacement for an
organization's approved evidence-handling procedure.

## 2. What the application can do

### 2.1 Media provenance analysis

The `/api/v1` media pipeline can:

- validate file signatures and configured size, pixel, and dimension limits;
- inspect image and video dimensions, formats, and metadata;
- inspect optional C2PA provenance manifests;
- calculate tiled Error Level Analysis (ELA);
- calculate tiled noise-residual signals;
- identify spatially validated copy-move regions;
- compare media against optional known-item references;
- sample video frames and retain the strongest frame-level evidence;
- apply deterministic R1-R4 evidence-fusion rules;
- report evidence tier, uncertainty, limitations, and supporting signals;
- render heatmaps where available;
- export a completed report as offline HTML;
- evaluate labeled images through a provenance-aware manifest.

A strong signal is not proof of manipulation. Compression, resizing, editing,
transcoding, and platform processing can create forensic artifacts in
authentic media.

### 2.2 Evidence ingestion

The investigation pipeline accepts structured and semi-structured evidence,
including:

- JSON and JSONL records;
- CSV records;
- Linux authentication logs;
- web access logs;
- Windows event XML;
- Firefox history databases;
- Chromium-style browser history and application/access records;
- filesystem metadata and other supported access records.

Malformed records are represented as parser warnings where possible instead of
silently being treated as valid evidence.

Each imported record is normalized into a common event model containing fields
such as:

- event identifier;
- case and evidence identifier;
- UTC timestamp;
- original timezone information;
- actor;
- host;
- normalized action;
- object or path;
- outcome;
- source IP;
- source reference;
- raw text;
- parser warning;
- source-specific details.

The fixed action vocabulary includes logon, logoff, privilege, file,
process, network, web, account, service, configuration, and `unknown`
actions.

### 2.3 Case and workflow management

The v2 workflow provides tenant-scoped case management:

- create and list cases;
- view a case;
- transition cases from `open` to `in_review` to `closed`;
- reopen a closed case only with a reason;
- register and list evidence;
- retrieve evidence details;
- soft-delete evidence;
- hard-delete evidence through the administrator-only path;
- create and list investigation notes;
- create and list controlled case tags;
- bookmark events or findings;
- change finding status to `new`, `confirmed`, or `dismissed`;
- require a dismissal reason;
- record workflow mutations in the audit log.

Soft-deleted evidence is excluded from evidence listings and timeline results.
Hard deletion also removes the associated normalized events and securely
deletes locally stored bytes. Production object-storage deletion must still be
implemented according to the deployed provider's versioning and retention
rules.

### 2.4 Timeline reconstruction

The normalized timeline provides a consistent chronological view across
different evidence sources. Investigators can filter by:

- actor;
- host;
- source type;
- action;
- minimum severity;
- date/time range;
- incident.

Timeline results support bounded cursor pagination. Cursors are URL-safe and
ordered by timestamp plus event identifier, preventing duplicate records when
pages are read sequentially.

### 2.5 Suspicious-activity detection

The current engine is deterministic and explainable. It can identify:

- repeated authentication failures followed by a successful logon;
- successful logons outside configured working hours;
- privilege escalation or privilege-use sequences;
- abnormal file-read bursts relative to an actor's imported baseline;
- bursts of destructive file deletion;
- configured multi-event sequences;
- related events grouped into incidents.

Every finding contains:

- a rule identifier;
- title and severity;
- confidence value;
- cited event identifiers;
- actor and host when available;
- start and end of the event window;
- explanation;
- known limitations;
- review status.

These are investigation leads, not automatic conclusions. A human reviewer
must interpret the evidence in context.

### 2.6 Chain of custody

For imported evidence, the application can:

- calculate and retain SHA-256 hashes;
- append custody operations to a tamper-evident HMAC chain;
- verify the custody chain;
- record ingestion and workflow actions;
- anchor local custody tips to a separately retained local file;
- detect changes during later verification.

The local implementation provides integrity and tamper detection. It does not
yet provide a trusted external RFC 3161 timestamp, a public transparency-log
witness, or a full PKI-based authenticity assertion.

### 2.7 Evidence-grounded assistant

The offline assistant performs deterministic retrieval over imported evidence
and returns citations to matching event identifiers. It is intentionally
conservative:

- it does not invent an incident narrative;
- it does not create findings;
- it does not replace investigator judgment;
- it can expose limitations when the evidence is incomplete.

An external AI provider may be integrated later, but that requires an explicit
privacy, retention, cost, provider, and validation decision.

## 3. Main user workflow

### Step 1: Create a case

Create a case with a meaningful title, such as `Suspected account compromise -
server-02`.

### Step 2: Collect and preserve source files

Keep the original evidence files unchanged. Record where they came from, who
collected them, and the collection time according to the organization's
evidence procedure.

### Step 3: Ingest evidence

Upload supported logs, history databases, metadata exports, or access records.
Select the parser that matches the source format. The service stores metadata,
hashes the uploaded bytes, and normalizes records into events.

### Step 4: Review parser warnings

Check warnings for missing timestamps, unsupported lines, assumed timezones,
or incomplete source fields. A timeline is only as reliable as the source
records and their interpretation.

### Step 5: Review the timeline

Start with the complete timeline, then filter by actor, host, action, source,
severity, incident, or time range. Use cursor pagination for large cases.

### Step 6: Review findings

Open each finding, inspect its cited events, compare it with surrounding
activity, and confirm or dismiss it. A dismissal must include a reason.

### Step 7: Add investigator context

Use notes for observations, tags for controlled classification, and bookmarks
for events or findings that must be revisited or included in a report.

### Step 8: Manage the case lifecycle

Move the case to `in_review` when analysis begins and to `closed` when the
review is complete. Reopening requires a documented reason.

### Step 9: Verify custody and export results

Verify the custody chain before relying on the evidence record. Export or
retain the case report according to the organization's retention policy.

## 5. Architecture

The application is organized into several boundaries:

- `app/main.py`: FastAPI routes, request validation, authentication boundary,
  job handling, and API responses.
- `app/forensics/models.py`: strict normalized event, finding, and workflow
  request models.
- `app/forensics/parsers.py`: source-specific parsers.
- `app/forensics/rules.py`: deterministic suspicious-activity rules.
- `app/forensics/incidents.py`: sequence matching and incident grouping.
- `app/forensics/persistence.py`: tenant-scoped SQLAlchemy models and
  repositories.
- `app/forensics/custody.py`: HMAC custody operations.
- `app/storage.py`: local artifact storage boundary.
- `app/queue.py`: inline/local queue boundary and production queue settings.
- `app/static/`: browser interface.
- `alembic/`: versioned database migration configuration.

### Local profile

The local profile uses:

- SQLite;
- local filesystem storage;
- in-process task execution;
- optional local bearer authentication;
- deterministic rules;
- offline media analysis;
- local audit and custody records.

### Production profile

The documented production boundary expects:

- PostgreSQL with managed Alembic migrations and backups;
- private S3-compatible object storage;
- Redis and a separately deployed RQ worker;
- OIDC/OAuth2 authentication and role enforcement;
- distributed rate limiting;
- controlled audit-log retention and export;
- encrypted transport and operational monitoring.

The local profile is suitable for evaluation, demonstrations, and controlled
investigation work. It is not a production internet-facing deployment.

## 6. Advantages

### Explainability

Findings cite source events, include rule identifiers, and expose limitations.
Investigators can inspect the evidence behind a result instead of receiving an
unverifiable score.

### Offline and privacy-oriented operation

The basic workflow does not require an external AI provider, API key, hosted
dataset, or cloud account. Sensitive evidence can remain on the investigation
machine.

### One workflow for different evidence types

Logs, browser history, application records, filesystem metadata, and media
signals can be handled within the same case-oriented process.

### Reproducibility

Deterministic parsers, rules, synthetic fixtures, hashes, and tests make it
possible to repeat an analysis and compare changes.

### Tenant-aware data isolation

v2 repository operations apply tenant filters consistently and avoid disclosing
whether another tenant's case or evidence exists.

### Controlled human review

Case statuses, finding statuses, notes, bookmarks, tags, dismissal reasons, and
audit entries preserve the investigator's decisions and context.

### Safe failure behavior

Unsupported or malformed inputs become explicit errors or warnings. Optional
detectors report `not_determined` when unavailable rather than silently
claiming a clean result.

### Extensibility

Parser, storage, queue, authentication, and database boundaries allow the
offline implementation to evolve toward PostgreSQL, S3, RQ, OIDC, and external
AI services without replacing the evidence model.

## 7. Current limitations and release gates

The following items are not complete production capabilities:

- OIDC/JWT authentication, organization roles, and administrative RBAC;
- ClamAV scanning, upload quotas, and archive rejection;
- external RFC 3161 timestamp anchoring;
- PostgreSQL operational deployment and backup/restore automation;
- production S3 implementation and object-version deletion handling;
- separately deployed RQ worker;
- distributed rate limiting;
- citation validation for an external AI reasoning provider;
- complete v2 browser dashboard and comprehensive report export;
- EVTX parser coverage;
- calibrated real-world forensic accuracy claims;
- full-frame/adaptive video and audio synchronization;
- C2PA signing and full chain visualization;
- detector drift monitoring and alerting.

These limitations matter because a local deterministic prototype is not the
same as a production evidence-management system with organizational identity,
external trust anchors, operational redundancy, and formally reviewed
retention controls.

## 8. Security and privacy guidance

- Keep the local profile off the public internet.
- Do not commit `.env` files, API keys, private images, or consent records.
- Treat uploaded filenames and source fields as untrusted input.
- Preserve original evidence separately from application-derived artifacts.
- Review timezone assumptions and parser warnings.
- Restrict access to case data and custody records.
- Configure retention for uploads, reports, backups, object versions, and
  derived files consistently.
- Use authenticated transport and OIDC before exposing a deployment.
- Do not send sensitive evidence to an external AI provider without an
  approved data-processing decision.
- Do not interpret a deterministic finding as proof without human review.

The repository's [privacy policy](./PRIVACY.md) and
[production architecture](./PRODUCTION_ARCHITECTURE.md) describe the current
storage and deployment boundaries in more detail.

## 9. Installation and validation

The shortest local setup is:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements-dev.txt
python -m uvicorn app.main:app --reload
```

Open `http://127.0.0.1:8000` in a browser.

Run the automated suite from the repository root:

```powershell
python -m pytest -q
```

The current implementation has been validated with **128 passing tests** and
one third-party deprecation warning. The workflow tests cover allowed and
forbidden transitions, reason validation, tenant isolation, pagination,
evidence deletion behavior, notes, tags, bookmarks, and timeline filtering.
